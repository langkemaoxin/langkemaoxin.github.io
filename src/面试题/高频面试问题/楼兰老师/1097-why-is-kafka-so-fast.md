## ① 顺序写：重新定义磁盘速度

![image](/面试题/高频面试问题/楼兰老师/1097-why-is-kafka-so-fast/img-87c15f2e193e.png)

大家普遍有个印象：磁盘很慢。没错，但说的是“随机读写”的磁盘。想象一下，你不是在笔记本最后接着写，而是在中间某一页找个空白地儿硬塞几个字，是不是很费劲？磁头在盘片上疯狂寻道，就像你疯狂翻页一样，这当然慢！

但 Kafka 不这么玩。它采用**顺序追加写入**，就像记笔记一样，永远只在文件末尾添加新内容。

看这张图，数据流（Writes）源源不断地写向每个分区（Partition）的末尾。而每个文件，在磁盘上都是提前申请的一块连续空间。磁头几乎不需要来回寻址，只管“一路向西”，这种操作的效率，快到可以和内存的随机读写掰手腕。Kafka 用最有效的方法，驯服了磁盘这头猛兽。这种顺序写的思想，也成了很多其他中间件提升日志写入效率的参考思想。

## ② 页缓存：把“急事”交给操作系统

![image](/面试题/高频面试问题/楼兰老师/1097-why-is-kafka-so-fast/img-1bd405e3736f.png)

如果每次写入都要等磁盘“确认收货”，那 Kafka 早就堵死了。所以，它请了个“外援”——操作系统的**页缓存（Page Cache）**。

看这张图，当 Producer 的消息过来，Kafka 把它“啪”一下丢进内存里的 Page Cache 就立刻告诉 Producer：“好了，搞定！”。它自己不用管什么时候、怎么把数据写到磁盘上。

这个“脏活累活”甩给了谁？操作系统。OS 会在它觉得合适的时候（比如凑够了一批数据，或者系统不忙时），自己把 Page Cache 里的数据批量刷到磁盘（disk）上。

这就像你收快递，快递员把包裹放前台（Page Cache）就行了，他不用等你亲自下楼取货（写入 Disk）。这样一来，写入操作的响应时间就大大缩短，应用的吞吐量自然就上去了。

但这种甩手掌柜的做法也是有不足之处的。最大的问题就在于你不知道操作系统什么时候进行刷盘操作，那如果出现了服务器故障，你也无法确保PageCache里的缓存信息能不能安全写到磁盘上。也就是没法保证数据安全。

解决的方法最好是写一条日志就申请一次刷盘操作，也就是称为同步刷盘。但是刷盘性能低，会影响应用的吞吐性能，而且过于频繁的刷盘操作还会加大操作系统的负担。这中间要怎么平衡？你可以参考下RocketMQ是如何设计刷盘策略的。评论区告诉我你的答案。

## ③ 同步副本：在速度与可靠间找到黄金平衡

![image](/面试题/高频面试问题/楼兰老师/1097-why-is-kafka-so-fast/img-86c67511bfa1.png)

快是很快，但万一 Kafka 节点挂了，内存里的数据不就丢了？为了不让数据丢失，Kafka 设计了**同步副本（In-Sync Replicas, ISR）**机制。

看这张图，一个 Producer 推送消息，首先到达 Leader 副本。但 Leader 不会马上回复“成功”，它会等消息被同步到 ISR 集合里所有的 Follower 副本那里，并且收到它们的“确认回执”后，才向 Producer 最终确认。

这是一种精妙的平衡。如果等所有副本都同步完，太慢；如果不等任何副本，太危险。ISR 机制确保了只要核心的、“在状态”的副本都收到了，数据就不会丢，同时又不会因为个别慢悠悠的副本而拖慢整个系统的速度。这叫“靠谱地快”！

当然，这里还有一个补充的问题，如何快速又准确的维护ISR列表呢？当有节点出现故障，甚至主节点发生了切换，怎么保证集群内的ISR列表快速更新并尽快同步呢？评论区告诉我你的答案，也给自己做做自测。

## ④ 分段+索引：给海量数据装上 GPS

![image](/面试题/高频面试问题/楼兰老师/1097-why-is-kafka-so-fast/img-0c60939bb8e1.png)

Kafka 的日志文件动辄上 T，如果消费者要找某条消息，难道要从头到尾扫描一遍？那不叫大数据技术，那叫“愚公移山”。

Kafka 的办法是**分段（Segment）+ 索引（Index）**。

看这张图，一个巨大的 Topic 会拆分成很多Partitioni分区，每个分区的日志优惠被切成一个个小的Segment日志文件 `.log` 文件。同时，Kafka 会为每个 Segment 配备一个 `.index` 索引文件和一个 `.timeindex` 时间索引文件。

这个index索引是用来帮助从日志中检索消息的。但是他被设计成“稀疏索引”，它不记录每条消息的位置，而是每隔一段才记录一条。当你要找 offset 为 180 的消息时，它先通过索引快速定位到“180 大概在 175 之后”，然后就可以从12496位置开始进行扫描，迅速找到目标。

这就像查字典，你先通过目录也就是索引，找到页码范围也就是Segment，再按拼音也就是Offset,快速定位，而不是从第一页开始翻。给海量数据装上 GPS，查找速度自然是数量级的提升。而且，通过这种稀疏索引的设计，也可以避免索引自己太过庞大的问题。

另外，Kafka也同时记录了.timeindex文件，这也是个辅助消息检索的索引文件。他是干什么用的？又是如何加快消息检索的？评论区告诉我答案。

## ⑤ 零拷贝：打通数据传输的“任督二脉”

![image](/面试题/高频面试问题/楼兰老师/1097-why-is-kafka-so-fast/img-b5823e85d730.png)

这是 Kafka 性能的王牌，也是面试的终极难题——**零拷贝（Zero-Copy）**。

先看左边的传统 I/O。数据从磁盘读到内核的页缓存，然后 CPU 把它拷贝到用户态的应用程序内存，应用程序再调用 `write()`，CPU 又把它拷贝回内核态的 Socket Buffer，最后才发给网卡。全程 **4 次拷贝，4 次上下文切换**，CPU 累得像个搬运工。

再看右边的零拷贝。Kafka 直接使用 `sendfile` 这类系统调用。数据从磁盘读到页缓存后，CPU 不再参与搬运，而是给出一个指令：“把这段数据从页缓存直接发到网卡”。数据直接在内核态就完成了传输。全程只有 **2 次拷贝，而且其中没有 CPU 拷贝，全是DMA拷贝，2 次上下文切换**。

CPU 从繁重的搬运工作中解放出来，专注于更重要的计算。数据传输的“任督二脉”被打通，效率极致，这就是零拷贝的威力。

零拷贝本身不难理解，但是如何把这个操作系统当中的复杂操作用简单清晰的方式表达出来，这也是应对面试的一种重要能力。

## 从优秀到卓越

好了，盘到这里，我们再回顾一下 Kafka 的五大性能法宝：

![image](/面试题/高频面试问题/楼兰老师/1097-why-is-kafka-so-fast/img-2297f1151ece.png)

### 核心回顾：

- **顺序写**：化“盘”为“存”，把磁盘的潜能压榨到极致。
- **页缓存**：借力 OS，让写入操作快如闪电。
- **同步副本**：在不丢数据的前提下，尽可能地快。
- **分段索引**：给 TB 级数据查找装上导航。
- **零拷贝**：把 CPU 从无意义的搬运中解放出来。

你看，把这些点串起来，才构成了一个完整的高性能体系。
