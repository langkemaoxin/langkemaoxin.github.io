在面试中，有这样一个“送命题”：“简历上写着你负责过核心链路优化，来讲讲你是怎么做的？”

很多同学一听到这个问题，脑子里瞬间一片空白，支支吾吾半天，最后憋出一句：“呃……我给数据库加了个索引。”

**就这？**

加个索引也叫系统架构优化？如果流量突增怎么办？主从延迟怎么解决？频繁 Full GC 导致的卡顿怎么调优？

真正的性能优化，绝不是“头痛医头”的单点修补，而是一场对**CPU、内存、磁盘 I/O、网络带宽**的极致平衡艺术 。它需要你具备全局视野，打出一套从数据库到架构，再到 JVM 底层的**“组合拳”** 。

![image](/面试题/三高架构/1352-how-to-perform-system-performance-optimization/img-4317783d562f.png)

今天，我们就来拆解这套高薪面试必问的打法。

## 第一拳：数据库层面——别只盯着索引看

接口响应慢，90% 的锅确实在数据库，但优化数据库可不仅仅是 `CREATE INDEX` 这么简单。

### 1. 你的索引真的生效了吗？

你以为加了索引就万事大吉了？**Tell me why?** 如果你的 SQL 写得烂，导致索引失效呢？如果区分度不够呢？ 面试官想听的不是你加了哪个字段，而是你有没有看过 **执行计划（Explain）**。 你需要明确指出，你是如何通过分析 Explain 结果，区分 `type=ALL`（全表扫描）和 `type=Ref/Range`（索引扫描）的 。

### 2. 单表破千万，索引也救不了你

当数据量达到千万级，B+树变深，磁盘 I/O 依然是瓶颈。这时候你必须展现出架构思维：**分库分表**。

- **水平拆分**：按用户 ID 取模，把数据拆分到不同的库表中，降低单表数据量 。
- **冷热分离**：这也是高手常用的思路。将近期 3 个月的订单（热数据）和历史订单（冷数据）物理隔离 。99% 的查询命中热库，速度自然起飞 。

![image](/面试题/三高架构/1352-how-to-perform-system-performance-optimization/img-efcf8d28b1d2.png)

## 第二拳：缓存层面——并发的银弹与陷阱

数据库调优到了极致，磁盘 I/O 依然慢怎么办？**Look at me!** 既然磁盘慢，那就用内存啊！**空间换时间**，这是性能优化的核心心法 。

引入 Redis 确实能让 QPS 起飞，但它也带来了致命的新问题，面试官就在这等着你：

### 1. 数据一致性怎么保？

你改了数据库，缓存里还是旧数据，用户看到的是“老黄历”，怎么办？  你是选择“先删缓存再更库”，还是“延时双删”？亦或是使用 **Canal** 监听 Binlog 进行异步更新？你需要准备一套完整的方案。

### 2. 缓存三灾：雪崩、穿透、击穿

- **缓存雪崩**：Redis 挂了或者大面积 Key 同时过期，流量瞬间打垮数据库 。**对策**：设置随机过期时间，或者引入 **Hystrix/Sentinel** 做熔断降级 。
- **缓存穿透**：恶意请求查询不存在的数据，直接穿透缓存打到库 。**对策**：布隆过滤器或缓存空对象 。

![image](/面试题/三高架构/1352-how-to-perform-system-performance-optimization/img-30c9e6ddb5a0.png)

## 第三拳：架构层面——解耦与异步

数据库和缓存都搞定了，系统 CPU 还是飙高，吞吐量上不去，**嗯哼？** 打开代码一看，你是不是在主流程里同步调用了第三方的短信接口、或者做复杂的报表计算？

**你这是在谋杀系统！** 网络 I/O 是很慢的，同步调用会导致线程长时间阻塞（Blocked），线程池瞬间被打满，新的请求进不来 。

![image](/面试题/三高架构/1352-how-to-perform-system-performance-optimization/img-c51b4b6a3038.png)

这就需要引入 **消息队列（MQ）**，比如 RocketMQ 或 Kafka 。

- **异步解耦**：用户下单后，发消息给 MQ 立刻返回“下单成功”，剩下的扣库存、发积分、发短信，让消费者（Consumer）慢慢处理 。
- **削峰填谷**：面对流量洪峰，MQ 可以暂存请求，让后端系统按自己的处理能力平滑消费，避免系统崩溃 。

## 第四拳：JVM 与底层——最后的阵地

架构都调整了，系统偶尔还是会有“幽灵卡顿”，耗时忽高忽低，为什么？ **Look in my eyes!** 去看你的 GC 日志！

### 1. 频繁 Full GC 的祸害

是不是 Young 区设置太小，导致对象过早晋升到 Old 区？是不是大对象直接进了 Old 区？ 频繁的 Full GC 会触发 **STW (Stop The World)**，整个世界都暂停了，你代码写出花来也没用 。 **优化方向**：合理设置堆内存参数（`-Xms`, `-Xmx`），选择合适的垃圾收集器（G1 或 ZGC）来减少 STW 时间 。

### 2. 线程池的陷阱

你还在用 `Executors.newCachedThreadPool()` 吗？ 这是一个巨大的陷阱！它会无限制地创建线程，导致 CPU 都在做**上下文切换**，甚至引发 OOM 。 **专业做法**：使用 `ThreadPoolExecutor` 手动创建线程池，根据业务是 **CPU 密集型** 还是 **IO 密集型** 来精细化配置核心参数 。

## 总结

所以，兄弟们，所谓的高并发系统性能优化，从来不是某一个点的单打独斗。

- **数据库**：从索引到 Explain，再到分库分表、冷热分离 。
- **缓存**：利用 Redis 空间换时间，还要防住雪崩和穿透 。
- **架构**：利用 MQ 进行异步解耦和削峰填谷 。
- **JVM**：通过 GC 调优和线程池管理，压榨最后一滴硬件性能 。

这一套**“组合拳”**打下来，才叫真正的系统优化 。从被动救火到主动规划，这才是架构师该有的样子 。

以后面试官再问你性能优化，别再只会说“加索引”了。**懂了吗？**
