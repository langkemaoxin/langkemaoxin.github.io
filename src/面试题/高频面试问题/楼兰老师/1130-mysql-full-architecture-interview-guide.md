## **第一个模块：基础架构 —— 五层都答不全，还说 “熟悉”？**

![image](/面试题/高频面试问题/楼兰老师/1130-mysql-full-architecture-interview-guide/img-1457ad0d727f.png)

面试官必问：“一个SQL语句在MySQL中是如何执行的？” 你只说 “SQL解析，数据检索”—— 错！大错特错！记好这 “五层逻辑链”，少一层都不行：

1. **客户端层**：就是你 Java 代码里的 JDBC、MyBatis 连接，没啥说的，但得提 “不是直接连服务端”，铺垫下一层；
2. **连接层**：核心是 “认证 + 连接管理”！比如客户端输账号密码在这验证，还会维护连接池（避免频繁创建连接），面试提 “Connectors 组件”，面试官立马觉得你懂细节；
3. **服务层**：MySQL 的 “大脑”！SQL 进来先过 “解析器” 拆语法（比如识别 select、where），再用 “优化器” 选最优计划（比如选 idx_name 索引还是全表扫），最后 “执行器” 调用存储引擎，这三步一个都不能漏；
4. **存储引擎层**：不是 “MySQL自带 InnoDB”，是 “MySQL实现了 InnoDB和MyISAM等多种存储引擎”！面试说这句话，能避开 80% 的基础坑；
5. **文件系统层**：数据最终存在这，比如 InnoDB 的.ibd 文件（数据 + 索引）、MyISAM 的.MYD（数据）和.MYI（索引），提具体文件名，显得你真拆过 MySQL 目录！

关于这个基础架构，有时间你再补充一点SQL优化策略，执行计划分析，这些都是妥妥的加分项。

## **第二个模块：存储引擎 —— 只知道 InnoDB，等于没懂！**

![image](/面试题/高频面试问题/楼兰老师/1130-mysql-full-architecture-interview-guide/img-d61a0670db03.png)

面试官最常问的问题：“MySQL有哪些存储引擎？各适合啥场景？” 如果你就只记得一个InnoDB，那等于白记。因为没有对比，你是说不清楚什么是InnoDB的。记住这几种常见的引擎，尤其是InnoDB和MyISAM，面试全覆盖：

1. **InnoDB**：必说 3 个核心 —— Undo Log（实现MVCC，这是MySQL事务的基础）、行锁（高并发写不卡）、聚簇索引（查主键快），适用于高并发写、多事务的场景。现在的Java 项目里基本全在用它；
2. **MyISAM**：表锁（写时全表锁）、无事务，只适合 “纯读场景”，比如报表统计，生产环境早被淘汰，但作为InnoDB的对比方案，会更显专业；

另外几个稍微了解一下就行。

1. **Memory**：数据存内存，快但重启丢数据，适合 Java 里的 “临时计算表”（比如统计近 10 分钟订单）；
2. **Archive**：高压缩比，只支持插入和查询，适合 “归档数据”（比如 3 年前的日志表）。

现在基本都只用InnoDB了。下次介绍InnoDB时，你要是能够跟MyISAM对比一下介绍InnoDB的优点，绝对能让面试官眼前一亮！

## **第三个模块：索引机制 —— 别只会说 “B + 树快”，说不出为啥快！**

![image](/面试题/高频面试问题/楼兰老师/1130-mysql-full-architecture-interview-guide/img-07cc1dcad5f9.png)

面试官灵魂拷问：“联合索引 (a,b) 查 where b=10 为啥不走索引？聚簇索引和非聚簇索引有啥区别？” 你只说 “不知道，反正加索引就快”—— 等于白说！记好这 “3 个核心点”：

1. **联合索引要守 “最左前缀”**：建了 (a,b)联合索引，查 a和a+b 能走索引，但单查 b 绝对不走！这是索引提速的基础。
2. **主键 vs 二级索引**：InnoDB 主键是 “聚簇索引”，数据存在索引里，二级索引 存的是 “主键值”，查二级索引要 “回表”，也就是再查主键，面试提 “覆盖索引能避免回表”（比如查 id+name，建联合索引 (id,name) 就不用回表）；
3. **MySQL为什么选择B + 树**：非叶节点只存索引（省内存）、叶节点是链表（支持范围查），Java 里查 “id>100 的订单”，B + 树直接遍历叶节点的链表就可以了，简单高效！

谈到索引，再来分析下B+树索引结构、相比于B树有哪些好处，又是 一波装逼的好机会。

## **第四个模块：事务机制 —— 只说 ACID，等于没懂底层！**

![image](/面试题/高频面试问题/楼兰老师/1130-mysql-full-architecture-interview-guide/img-755dd0262e1a.png)

面试官追问：“事务的原子性靠啥实现？InnoDB 的可重复读怎么解决幻读？” 你只说 “ACID 重要”—— 面试官心里已经给你打低分了！

1. **ACID 不是空话**：原子性靠 Undo Log进行事务回滚、持久性靠 Redo Log，进行崩溃恢复、隔离性靠锁和 MVCC、一致性是最终目标，面试把 理论和技术绑在一起说，专业度拉满；
2. **隔离级别要讲 “解决啥问题”**：读未提交，可能产生脏读 → 读已提交，解决脏读，可能产生不可重复读 → 可重复读 解决不可重复读，是MySQL 默认的隔离级别→串行化 没有并发问题，但是性能非常低，基本不会用。
3. **脏读、幻读、不可能重复读，不要只记名字，要记案例。**比如幻读，你就记一个案例，同一个事务多次查询 id between (0,10) 时，可能有其他事务插入或者修改了条件范围内的数据，就会出现在同一个事务中多次查询结果行数发生变化的问题。解决的方法就是把 0到10 的数据锁住，不让其他事务修改就行了。这就是InnoDB的 行锁+间隙锁 的方案。把这案例一说，比你做任何解释效果都要好。

接下来，如果你能再聊聊单数据库的XA事务协议实现，以及由此扩展出来的多数据库的分布式事务解决方案，绝对让面试官对你高看一眼。

## **第五个模块：日志系统 ——Redo/Binlog 分不清，面试必挂！**

![image](/面试题/高频面试问题/楼兰老师/1130-mysql-full-architecture-interview-guide/img-2616b4eb1417.png)

面试官常见的问题：“Redo Log、Undo Log、Binlog 有啥区别？MySQL 写数据先写哪？” 你只说 “都是日志”—— 直接凉！记好这 “3 日志 + 1 机制”：

1. **Redo Log**：“保证持久化”，记录数据页修改，写数据时先写它（WAL 机制：Write-Ahead Logging），崩溃了靠它恢复，文件是循环写的（不会无限大）；
2. **Undo Log**：“保证原子性”，记录数据修改前的状态，回滚事务就靠它，还能实现 MVCC（多版本并发控制）；
3. **Binlog**：“记录所有写操作”，比如 insert、update，主从复制靠它（主库发 Binlog，从库读），数据恢复也靠它，是追加写的（会无限大，要定时删）；
4. **写数据顺序**：MySQL是先写 Redo Log→再写 Binlog→最后写数据文件，面试说这个顺序，绝对显实战！

这些日志当然不能死记，结合你的工作经历，整理几个根据日志进行问题排查的经验，面试官都要对你竖大拇指。

## **第六个模块：高可用架构 —— 只知道主从，太浅了！**

![image](/面试题/高频面试问题/楼兰老师/1130-mysql-full-architecture-interview-guide/img-ca4bef17fea5.png)

面试官聊嗨了，就会继续问：“生产环境 MySQL 怎么保证不宕机？分库分表用啥中间件？” 你只说 “主从复制”—— 不够！记好这 “3 架构 + 1 中间件”：

1. **主从复制**：也是“读写分离”的典型方案，主库记录Binlog，从库读Binlong写中继日志，再通过中继日志保持数据同步。但主从复制要手动切主库，适合中小规模；
2. **MGR 集群**：“自动故障转移”的典型方案，3 个节点以上组成集群，主库挂了自动选新主，还支持强一致性（数据同步完再返回），Java 项目里高可用首选；
3. **分库分表**：“解决单机性能瓶颈”的典型方案，水平分片（按用户 id 分，比如 id%2 分 2 库）、垂直分片（按业务分，比如用户库和订单库分开）、分布式主键、分布式事务等等问题接踵而来，没有一点实力还真hold不住；
4. **中间件**：Java 项目里用 ShardingSphere，不用自己写分片逻辑。但是注意，面试想要提 “用过 ShardingSphere 做水平分片”，那你最好是真的做过，不然很容易露馅的。

当然，如果你有能力再自己发挥一下，补充一些基于Binlog进行数据同步经验，以及一些ShardingSphere组件分库分表的应用经验，你还怕面试官不让你通过吗？

最后，MySQL 架构面试不可怕，就怕你只会背 “八股文”，不会说 “底层逻辑”！今天这 6 个模块：基础架构、存储引擎、索引、事务、日志、高可用，每个都给你整理出了最核心的基础框架，下次再被问，你按这个框架进行扩展，加上一点实际经验来回答，面试官会觉得 “你是真用过、真研究过，不是瞎写简历”！
